GEM orchestrates a team of 6 concurrent agents — each running as a separate process — through a shared Markdown-based blackboard. The Supervisor agent uses Gemini's function-calling to dispatch tasks to the right sub-agent, while a custom proxy-tool pattern bridges the LLM's native tool-use with the multi-process architecture.

Architecture

Most LLM wrappers are monolithic — one process, one model, synchronous tool calls. GEM takes a different approach: a Blackboard Architecture where decoupled agents communicate through a shared Markdown file using JSON-encoded tasks. This means agents can be added, removed, or crashed independently without bringing down the system.

Technical Highlights

1. Proxy tool pattern for multi-agent dispatch

create_blackboard_proxy() wraps each sub-agent's functions as callable tools for Gemini. When the LLM decides to "call" a tool, the proxy serializes the call as a JSON task on the blackboard and blocks until the sub-agent posts a result. This bridges native LLM function-calling with a multi-process architecture.

2. 11-model cascading fallback with key rotation

The Supervisor chains through 11 Gemini model variants × multiple API keys. Rate-limit (429) errors trigger key rotation first, then model fallback. Non-rate-limit errors skip directly to the next model. Chat history is preserved across switches.

3. JSON-over-Markdown IPC — no external dependencies

Inter-process communication uses plain file appends with --- delimiters and fenced JSON code blocks. No Redis, no RabbitMQ, no sockets. Agents are fully decoupled — add a new agent by creating a file and registering its tools.

4. Voice pipeline: wake word → STT → LLM → TTS

Custom .onnx wake word models from openWakeWord. faster-whisper runs locally (no cloud STT). piper-tts for neural speech synthesis. The entire pipeline runs without internet for the voice components.

5. Persistent memory with SQLite

The KnowledgeAgent stores user preferences, notes, and facts in a local SQLite database. The Supervisor's system prompt instructs it to proactively save new information about the user — building a personal knowledge base over time.

Known Limitations

  • Blackboard file I/O has no OS-level locking — concurrent agent writes can cause race conditions
  • Voice agent blocks during recording (synchronous record_until_silence)
  • No execution sandboxing for shell commands — trust is assumed
  • Knowledge base "semantic search" currently falls back to SQLite LIKE queries
  • Single user only — no auth or multi-tenant support
