Most portfolios are React apps or templates. This one has a process table, a syscall dispatch handler, and a virtual filesystem — compiled from C to WebAssembly via Emscripten. Every command you type in the terminal runs through actual C code. You are reading this document inside the thing it describes.

C → WebAssembly Emscripten Zero dependencies Vanilla JS

Why C instead of JavaScript

JavaScript was the obvious choice. C was the interesting one. WebAssembly gave a real compilation target — which meant deliberate memory layout decisions, a real build pipeline, and a binary that is fully self-contained. The kernel has no malloc from libc; memory tracking is manual against a 64 KB virtual budget. The output from every command is captured via a 4 KB ring buffer (buf_printf) instead of stdout — Emscripten's printf redirection was bypassed for performance. The constraint made the engineering more honest. A 31 KB binary with a working scheduler is a better portfolio piece than a Create React App template.

What I'd do differently

  • The MMU tracks a 64 KB virtual budget but doesn't enforce real memory isolation — actual isolation would require WASM memory segment manipulation that Emscripten doesn't expose
  • Content is baked into the binary at compile time — changing the resume means recompiling. A smarter VFS would lazy-load from a static JSON file
  • The 4 KB ring buffer in wasm_run_command is a hard truncation limit — commands generating more than 4 KB of output silently cut off
  • Window manager not optimized for many simultaneous windows
