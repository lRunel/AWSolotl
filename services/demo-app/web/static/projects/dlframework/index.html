Distributed training across personal devices — workers join and leave mid-run, training never stops, no sync barrier

Async SGD
no synchronization barrier

Most distributed training frameworks assume a fixed cluster. This one treats your personal devices as an opportunistic pool. A phone joins when it's idle. A laptop trains during lunch. Both can disconnect without stopping the run. The coordinator uses async SGD with staleness dropping — gradients are applied as they arrive, stale ones are discarded.

Why async SGD and why staleness dropping

PyTorch Distributed uses synchronization barriers — every worker must finish before the next step starts. That assumption breaks when workers are personal devices that sleep, lose WiFi, or run out of battery. Async SGD removes the barrier: the controller applies each gradient as it arrives (w = w − lr × gradient). But this creates a new problem — a gradient computed 50 steps ago on stale weights can push the model in the wrong direction. Staleness dropping solves this: the controller tracks gradient age and discards updates beyond a threshold.

The result is a training run that degrades gracefully when devices leave and recovers automatically when they rejoin.

Architecture

┌──────────────────────────────────────────┐
│         Controller (FastAPI :8000)       │
│                                          │
│  Global model · Dataset · Gradient buf   │
│  POST /register                          │
│  GET  /get_task  (weights + batch)       │
│  POST /send_gradients                    │
└────────────────┬─────────────────────────┘
                 │
       ┌─────────┼─────────┐
       │         │         │
  ┌────┴───┐ ┌───┴───┐ ┌───┴───┐
  │Worker 1│ │Worker2│ │WorkerN│
  │ laptop │ │ phone │ │termux │
  │  k=120 │ │  k=40 │ │  k=?  │
  └────────┘ └───────┘ └───────┘
  (join or leave at any time — training continues)

k = local training steps. The controller estimates k per worker based on its reported CPU, RAM, and bandwidth — slow phones get fewer steps per round.

Technical Highlights

1. Time-bounded computation

k is not fixed globally. Each worker reports its compute + bandwidth on registration. The controller assigns a k that fills the worker's available time window — a phone might get k=40 while a laptop gets k=120. Same wall-clock time, different work.

2. Staleness dropping

The controller tracks how many global steps have elapsed since a gradient was computed. Gradients older than the staleness threshold are discarded rather than applied — preventing stale updates from corrupting the model.

3. Android via Termux

Workers run on Android phones without modification — just Termux + pip install. No special mobile build, no app store.

Limitations

  • Tested only on MNIST / small CNNs — large models untested
  • LAN only — workers must reach controller IP directly
  • Gradient compression not implemented — bandwidth bottleneck
  • Staleness threshold is hardcoded, not adaptive
  • No multi-tenant support (one training run at a time)
